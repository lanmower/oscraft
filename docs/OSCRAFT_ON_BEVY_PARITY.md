## Decisions and reasons

- D1: Oscraft's Rust sim crate runs inside Bevy FixedUpdate as the one authority; Avian physics is not used for RTS units and stays for the planet and character scenes. Reason: The sim already owns fixed-point math and the state hash (CAP-DET-1, CAP-DET-2); physics would add a second source of truth for unit positions and break the hash.
- D2: RTS mode ticks at 16 Hz (oscraft SIM_TICKS_PER_SECOND); Bevy's 64 Hz stays for scenes that are not RTS. Reason: 16 Hz is the rate oscraft's orders, deltas and hashes are tuned to; 64 Hz would quadruple per-client bytes. The 60 and 64 Hz discrepancy between AGENTS.md and src/protocol.rs is settled by this choice and resolved in S2.
- D3: A headless Bevy server is the authority and replaces the browser host and its WebRTC data channels. Reason: Host-authoritative orders need one place that decides which units obey (docs/HOST.md); a browser tab that hosts ends the match when it closes.
- D4: Desync detection by per-tick state-hash comparison replaces lockstep input exchange (CAP-DET-6). Reason: Lockstep stalls every client on the slowest peer and cannot admit spectators or late joiners (docs/HOST.md, MAX_PLAYERS 10 with spectators); CAP-DET-6 has no gate today, and the hash comparison keeps the desync check that the lockstep claim was for.
- D5: Native clients use Lightyear over UDP; browser clients use WebTransport with WebSocket as the fallback. Reason: Lightyear is already the Bevy networking layer (Cargo.toml:14); WebTransport is the browser path nearest to UDP, and WebSocket covers browsers without it.
- D6: Nostr stays optional room discovery (kind 30078, announced every 15 s, expired at 45 s); game data does not travel over it. Reason: Discovery needs a public directory; relays are a poor data path for 16 Hz state and would expose match traffic to them.
- D7: Bevy 3D renders the client and HUD, and the browser build enables webgl2 next to webgpu. Reason: oscraft's browser path is WebGL2 today; a WebGPU-only build would drop browsers that do not have WebGPU.
- D8: The piccolo mod host is linked into the Bevy server and client with every script API unchanged. Reason: Every game function is kept (owner rule 2026-11-25), and piccolo is pure Rust, so it runs natively and in wasm without a second VM.
- D9: oscraft-replay 3 files stay readable and must replay to the same hashes in Bevy. Reason: The recorded replays are the regression oracle that the cutover in S6 is judged against.
- D10: Fog-filtered sends, delta snapshots and command batching are S5 transport work; the sim does not change to support them. Reason: A sim change would move the hash baseline that S1 and S2 are measured against.
- D11: The editor rows (CAP-MAP-10, CAP-ABIL-6, CAP-EVT-4) and the sound and chat rows (CAP-PRES-2, CAP-PRES-4) are owner-decided gaps, not planned stages. Reason: The spec names no stage for editors, audio or chat; giving them a stage would be a scope decision the owner has not made.
- D12: The second CAP-LUA-1 row (deterministic random numbers and string helpers) is renamed CAP-LUA-8. Reason: The parity ledger needs unique ids; the first CAP-LUA-1 is the row GAMEPLAY_PARITY cites (GP-MOD-6).
